# bAIble v2 — Public / Private Boundary

This is a hard publication boundary.

## Public material

Safe public material can include reusable principles, generic workflows, abstract architecture, terminology, generalized lessons, templates, synthetic examples and public references.

## Keep private

Do not publish secrets, credentials, personal identifiers, private conversations, private repository contents, customer/confidential data, proprietary implementation details, internal access paths, private run evidence, hidden context or sensitive experiments.

## Generalize before publishing

1. remove identifying details;
2. remove secrets and access paths;
3. remove unnecessary project-specific implementation detail;
4. rewrite the lesson so it stands alone;
5. check that a public reader can understand it without the private source;
6. preserve uncertainty and limitations;
7. perform final privacy review.

If a claim materially depends on inaccessible private evidence, either keep it private or clearly present it as a generalized lesson rather than pretending the evidence is public.

Public bAIble is not a backup of the private runtime.
