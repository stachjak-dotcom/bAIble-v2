# bAIble v2 — Build Plan

Status: ACTIVE / HUMAN-AUTHORIZED

## Goal

Produce the strongest living bAIble v2 we can currently justify from:
- the original bAIble foundation,
- bAIble pre-v2,
- FederAItion runtime and research,
- UnAiversed context/relationship work,
- explicit human decisions from the current collaboration.

The result must be usable by both humans and AI without pretending that documentation is implementation, that a record is truth, or that a remembered relationship is evidence.

## Canonical ecosystem

The system is treated as one ecosystem with three primary domains:

- **bAIble** — governance, language, reusable rules, roles, lessons, workflows and public orientation.
- **FederAItion** — project/runtime coordination, execution state, durable evidence, implementation and private operational history.
- **UnAiversed** — contextual and relational mapping space from which different views can be generated.

Two active entities create and use the ecosystem:
- **HI — Human Intelligence** — intent, material decisions, values, acceptance and intervention gates.
- **AI — Artificial Intelligence** — bounded interpretation, planning, execution, checking, recording and assistance according to role and scope.

None of the three domains is the universal source of truth. They have different responsibilities and must preserve their boundaries.

## Work split

### Phase 1 — Inventory and provenance
Collect reusable material from all three source domains. Classify each item as:
KEEP / MERGE / REWRITE / HISTORY / ARCHIVE / DROP.

Every migrated concept must preserve:
- origin,
- current meaning,
- evidence/status,
- public/private boundary,
- whether it is design, implementation, test evidence or verified behavior.

### Phase 2 — Canonical graph
Define one canonical semantic graph for the ecosystem:
- entities,
- mechanisms,
- roles,
- context items,
- relations,
- authority boundaries,
- epistemic states,
- failure modes,
- milestone links.

The graph is the model. Human and AI maps are views over it.

### Phase 3 — Human and AI views
Create two separate navigational views from the same graph.

**Human view** prioritizes:
purpose → orientation → current state → decisions → uncertainty → next action.

**AI view** prioritizes:
intent → role → scope → authorized sources → context → rules → expected evidence → verification → authorized next transition.

### Phase 4 — Failure modes
Attach risks directly to the objects and transitions they can distort. Do not exile them into a generic risk appendix.

Examples:
context drift, meaning drift, scope drift, false done, stale context, record ≠ truth, decision ≠ truth, authority leakage, public/private leakage, verification collapse, reminder overload.

### Phase 5 — Coordination and execution
Preserve the current responsibility split:
- rAIda = THINK / COORDINATE / REMEMBER-TO-CHECK
- Watchdog = CONTINUE / MONITOR / ESCALATE
- Reality Check = ALIGN working maps
- Fact Check = VERIFY factual/evidential claims
- Human = material decisions and intervention gates
- Agent = PREPARE / REASON / EXECUTE / RECORD
- Repository = durable memory
- Wolf = ORIENT / TEACH / ONBOARD
- WheeAIls = relevance/reminders without authority

### Phase 6 — Verification
For every significant claim about the system ask:
- Is this designed?
- Is this built?
- Was it tested?
- Was it verified at the claimed boundary?
- Was it integrated?
- Was it accepted by the human when acceptance is required?

Do not collapse these states.

### Phase 7 — Living release
A version is publishable when:
- public/private review passes,
- contradictions are listed explicitly,
- navigation works for both Human and AI views,
- duplicated onboarding material is consolidated,
- core terminology is stable enough to use,
- unresolved questions remain visible,
- source/provenance links exist where needed,
- the current version is materially better than the previous one without erasing useful history.

## Coordination protocol

Before a side-effecting change:
1. establish intent;
2. establish scope;
3. identify authority;
4. identify sources and rules;
5. identify expected evidence;
6. identify stop conditions;
7. execute only the authorized step;
8. record actual evidence;
9. verify at the appropriate boundary;
10. expose contradictions and unresolved uncertainty;
11. continue only through an authorized next transition.

## Epistemic conflict rule

A yellow or uncertain result is not sufficient when an actual contradiction was found.

For every material contradiction record:
- contradiction ID,
- claim A + source A,
- claim B + source B,
- contradiction type,
- what is unresolved,
- what evidence/check could resolve it,
- whether work may continue safely before resolution.

## Completion definition

bAIble v2 is never “finished forever.”

A release can be called a **current living baseline** only when its claims, boundaries, navigation and verification state are explicit enough that both a human and an AI can use it without silently inventing missing meaning.
